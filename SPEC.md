# psyholuh — спецификация первой версии

## 1. Спецификация

**Цель.** Личный локальный чат, в котором можно выговориться текстом или голосом и продолжить длинный разговор без ручного пересказа предыдущих событий. Публичный репозиторий должен показывать, как приложение собирает контекст, обрабатывает голос и сохраняет состояние между запусками.

### Сценарий пользователя

1. При создании беседы пользователь выбирает Claude или DeepSeek из списка моделей OpenRouter, настроенных на сервере. Backend сохраняет точный `model_id` в беседе. Выбор действует до конца её жизни.
2. Активна максимум одна беседа на локальную установку. Создание или открытие другой беседы меняет активную беседу. Данные сохраняются автоматически. Сохранённую беседу можно открыть и продолжить с её моделью и памятью. Новый диалог начинает собственную историю.
3. В интерфейсе слева список бесед, в центре лента, внизу поле ввода и микрофон. Текст ответа появляется по мере генерации. В беседе можно выбрать режим ответа «Выслушай» или «Помоги разобрать». Беседа запоминает режим последнего отправленного сообщения.
4. Запись с микрофона или загруженный аудиофайл расшифровывается локально. Готовая расшифровка появляется как редактируемый черновик. При явной отправке приложение одной операцией сохраняет подтверждённый текст и убирает черновик из списка.
5. В панели «Память» видны текущая сводка и источники заметок. Для последнего успешного ответа можно открыть старые реплики, которые приложение действительно включило в запрос.

### Память и контекст

- **Переписка.** SQLite хранит исходные реплики с порядковым номером внутри беседы, ролью, временем и статусом. Ответ дополнительно хранит фактически использованный идентификатор модели. История доступна после перезапуска и служит источником для повторной сборки памяти.
- **Сводка.** У каждой беседы есть версия сводки и номер последней покрытой реплики `covered_through_seq`. Воркер сжимает последовательные блоки из исходных сообщений, когда они выходят из окна. Сводка и её граница обновляются одной транзакцией.
- **Заметки.** События, предпочтения, открытые темы и уточнения хранятся со ссылками на реплики и временем. Слова пользователя, предположения и ответы модели различаются по происхождению. Исправление помечает старую запись как заменённую. Предыдущую формулировку можно найти в истории.
- **Поиск.** FTS5 индексирует сообщения и заметки. Поиск ограничен `chat_id`. Сборщик отбирает совпадения по текущему сообщению и недавним репликам, убирает дубли и при необходимости добавляет соседнюю реплику. Векторный поиск имеет смысл после проверки реальных русских перефразировок.
- **Запрос к модели.** Сборщик резервирует место для ответа и соблюдает бюджет выбранной модели. Он добавляет правила режима, сводку, несколько найденных фрагментов, непрерывный хвост свежих реплик и новое сообщение. В хвост входят отправленные сообщения пользователя и завершённые ответы. Прерванные ответы остаются в истории со своим статусом. На запрос записываются номера переданных старых реплик, границы хвоста, версия сводки и граница покрытия. Если поиск вернул заменённую запись, она явно помечается как историческая. Так панель памяти показывает реальный состав запроса.
- **Задержка сжатия.** Пока воркер догоняет, запрос включает исходные сообщения после границы сводки. Если хвост уже превышает бюджет, backend дожидается сжатия необходимого блока перед генерацией и показывает статус. Ошибка сжатия оставляет исходники и даёт повторить запрос. Если само новое сообщение превышает бюджет, backend сохраняет полный текст, разбирает его блоками и использует сводку блоков с привязкой к оригиналу. Этот режим виден в интерфейсе.

### Фоновые задачи и восстановление

- SQLite хранит исходные данные, статус задачи и результат. Строка задачи создаётся в SQLite одновременно с записью, которая требует обработки. В Redis/RQ передаётся идентификатор задачи. Воркеры читают запись и пишут результат в SQLite.
- У расшифровки и памяти отдельные очереди и воркеры. Отправка ответа остаётся в FastAPI. У каждого задания есть тип, `chat_id`, ссылка на входные данные, статус и счётчик попыток. Голосовой черновик относится к беседе, из которой отправили запись. После переключения или перезагрузки клиент заново получает её задания и черновики по `chat_id`.
- Диспетчер подбирает незавершённые задачи при запуске и периодически сверяет их с очередью. Повторная доставка безопасна. Расшифровка сохраняется в один черновик, а запись сводки сверяет предыдущую версию и границу. Старый результат не может затереть новый. Для временных ошибок предусмотрено ограниченное число повторов и видимое сообщение при исчерпании попыток.
- Отправленная реплика сохраняется перед генерацией. Один `request_id` закреплён за одной репликой и одним логическим ответом в беседе. При повторе активной генерации API возвращает статус текущей попытки. После прерывания первый повтор атомарно захватывает новую попытку для того же ответа. После успеха повтор возвращает сохранённый ответ даже при потере события `done`. Генерация с истёкшим сроком владения переводится в `interrupted`, поэтому после падения API её можно повторить. Запоздавшая попытка не может перезаписать ответ новой.

## 2. Технологии

| Компонент | Выбор | Назначение |
|---|---|---|
| Веб-интерфейс | React, TypeScript, Vite | Чат, запись с микрофона, поток ответа, список бесед и панель памяти |
| Python API | FastAPI, Pydantic | JSON-контракты, загрузка аудио, поток SSE |
| Модели | OpenRouter Chat Completions | Claude и DeepSeek для ответа. Для сжатия можно настроить отдельную модель |
| Данные | SQLite в режиме WAL, FTS5, версионируемые миграции | История, память, задачи и поиск на одном компьютере |
| Фоновые задачи | Redis, RQ | Доставка, изоляция расшифровки и суммаризации, повторы |
| Распознавание речи | `faster-whisper`, многоязычная модель | Локальная расшифровка русского аудио |
| Запуск | Docker Compose | Воспроизводимый локальный запуск API, UI, Redis и воркеров |

По умолчанию приложение слушает localhost. Ключ OpenRouter передаётся только серверу через окружение. SQLite, аудио, модельный кеш, `.env` и логи остаются вне Git. В репозитории предусмотрены `.env.example`, англоязычный README со схемой и инструкция запуска двух режимов.

Деморежим использует отдельную SQLite-базу с вымышленной историей и детерминированный адаптер. Он проходит через реальный сборщик контекста и показывает источники. В личном режиме OpenRouter получает отправленный текст и отобранный контекст. При облачном сжатии провайдер также получает сжимаемый блок переписки и предыдущую сводку. Расшифровка выполняется на компьютере. После успешной расшифровки или удаления черновика исходное аудио удаляется. При ошибке аудио доступно для повтора или ручного удаления.

## 4. План выполнения

### До параллельного старта

Основной чат фиксирует [контракт OpenAPI](api/openapi.yaml) и примеры запросов и событий. Backend и Frontend согласуют идентификаторы, статусы, ошибки и форматы. Reviewer проверяет контракт. Для реализации создаются две свежие рабочие ветки от одного согласованного состояния. Рабочие деревья разделены. Backend владеет `backend/` и Compose, Frontend владеет `frontend/`. Общий контракт и README сводит основной чат. Frontend использует моки контракта до готовности API.

| Контракт | Минимальное поведение |
|---|---|
| `GET /models`, `GET /chats`, `POST /chats`, `POST /chats/{id}/activate` | Список настроенных моделей и бесед, создание с `model_id`, явная активация. Возвращаемые данные указывают активную беседу |
| `GET /chats/{id}/messages` | Постраничная история в порядке `seq`, включая статусы ответа |
| `POST /chats/{id}/messages` | Принимает `text`, `mode`, `request_id` и `audio_id` при отправке черновика. Поток SSE передаёт `status`, `delta`, `done` или `error`. Повтор с тем же ID возвращает статус активной попытки, запускает попытку после прерывания или возвращает сохранённый результат. Тот же ID с изменёнными входными данными даёт конфликт |
| `POST /chats/{id}/audio`, `GET /chats/{id}/audio`, `GET /jobs/{id}` | Загрузка даёт `audio_id` и `job_id`. Список восстанавливает черновики и задания после перезагрузки. Задание показывает `queued`, `running`, `succeeded` или `failed` и при успехе даёт черновик |
| `POST /jobs/{id}/retry`, `DELETE /chats/{id}/audio/{audio_id}` | Ручной повтор доступен для ошибки расшифровки на том же аудио. Удаление убирает черновик и аудиофайл и останавливает публикацию запоздавшего результата |
| `GET /chats/{id}/memory` | Версия сводки, граница покрытия, заметки со ссылками и список старых реплик из запроса, связанный с ID последнего успешного ответа |

### Параллельная работа и интеграция

1. **Frontend и Backend стартуют одновременно.** Backend реализует BE-01 и подключает потоки текста, память и воркеры. Frontend реализует FE-01–04 по мокам, включая ожидание, прерывание и ошибки. Изменения общего контракта согласуются в основном чате до изменения обеих сторон.
2. **Интеграция проходит по вертикальным сценариям.** Сначала беседа и поток текста, затем голосовой черновик, затем сводка, поиск и панель памяти. Основной чат сводит деморежим, инструкции запуска и проверяет, что обе ветки используют один контракт.
3. **Независимое ревью.** Reviewer использует Astra Medium и проверяет документ, затем в ходе реализации проверяет контракт и интегрированную версию на соответствующих этапах. Он фиксирует находку, сценарий воспроизведения, нарушенный критерий и приоритет. Исправления вносит владелец соответствующей части, после чего проверяется затронутый сценарий.
4. **Готовность к публикации.** Основной чат проходит критерии на чистом локальном запуске и проверяет содержимое репозитория. Автоматизированные проверки выполняются через общий `make check` с конфигурацией вне репозитория. Демосценарий и README входят в пользовательский результат.

## 5. Критерии приёмки

| ID | Сценарий | Наблюдаемый результат |
|---|---|---|
| AC-01 | Создать беседу с Claude, написать сообщение, создать беседу с DeepSeek, открыть первую и перезапустить приложение | Активна максимум одна беседа. Первая продолжает использовать свой `model_id`. Обе истории сохраняются, и запрос к одной беседе не содержит данных другой |
| AC-02 | Прервать поток, отправить два одновременных повтора. Повторить испытание с разрывом между сохранением ответа и `done`, и с падением API во время генерации | Текст появляется частями. На одну реплику создаётся максимум одна активная попытка. После прерывания она восстанавливается, после успеха повтор возвращает ранее сохранённый ответ. Дубликатов реплик и ответов нет |
| AC-03 | Записать русское голосовое, открыть другую беседу, перезагрузить страницу и вернуться. Отредактировать и отправить расшифровку. Отдельно удалить черновик, пока обрабатывается его аудио | Черновик восстанавливается в исходной беседе. В историю попадает подтверждённый текст. Аудио остаётся на компьютере и удаляется после успеха или ручного удаления. Поздний результат удалённой записи не появляется |
| AC-04 | Замедлить воркер суммаризации и включить в историю один прерванный ответ. Отдельно отправить сообщение длиннее доступного бюджета | По `seq` сводка и хвост вместе покрывают все отправленные реплики и завершённые ответы до текущего хода. При нехватке места виден статус подготовки. Бюджет запроса соблюдается, а оригинал длинного сообщения остаётся доступен |
| AC-05 | Упомянуть встречу в среду, потом перенести её на пятницу. После сжатия спросить про встречу | В контексте пятница отмечена актуальной датой, а среда помечена заменённой, если поиск вернул её в запрос. Из панели памяти открывается исходное уточнение |
| AC-06 | Остановить воркер или Redis после записи задачи и запустить снова. Доставить один `job_id` повторно. Довести задачу расшифровки до исчерпания попыток и повторить вручную | Потерянная задача подбирается повторно. Повтор не создаёт второй черновик и не откатывает актуальную сводку. Интерфейс показывает ошибку и запускает новую попытку для той же записи |
| AC-07 | Запустить проект по README без API-ключа рядом с существующей личной базой | Открывается вымышленная беседа, работает демонстрация переноса встречи и переход к источнику. Личные сообщения отсутствуют в демоленте и демозапросах. Вызовов OpenRouter нет |
| AC-08 | Запустить личный режим с тестовым ключом OpenRouter и провести по одной короткой беседе на каждой модели. Проверить исходящие запросы при ответе и сжатии | Обе модели отвечают потоком с выбранными идентификаторами. Ошибка провайдера видна в интерфейсе. Запросы содержат текст и выбранный контекст или блок для сжатия. Ключ доступен серверу, исходное аудио остаётся локально |
| AC-09 | Сравнить панель памяти с фактическим входом последнего успешного запроса. В отдельной реплике высказать предположение и выбрать «Выслушай» | Панель указывает на реальные исходные реплики, а предположение остаётся атрибутированным пользователю. Режим отражается в инструкции ответа |
